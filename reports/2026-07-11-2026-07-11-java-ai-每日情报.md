## 四、AI 应用工程师每日小任务

1. 为一次模型调用增加超时、重试、错误分类和 fallback 文案，并在日志中记录失败原因、模型名称、请求场景和 traceId。
2. 设计一个工具调用白名单，只允许模型调用 2-3 个只读业务接口，并写清接口权限边界、入参校验规则和拒绝策略。
3. 对比 LangChain4j 与 Spring AI 的 `ChatModel`、`EmbeddingModel`、`VectorStore` 抽象差异，整理 5 条适合团队选型的结论。
4. 实现一个简单的意图识别 prompt，把用户问题分到问答、检索、任务执行、闲聊四类，并为每类设置不同的后续处理链路。
5. 为 RAG 检索结果增加最小观测指标：命中文档数、topK、相似度分布、最终引用文档 ID、无命中比例，方便后续排查回答质量问题。

## 五、对 Java 开发者的实际启发

Java AI 应用的重点正在从“能调用模型”转向“能稳定治理模型调用”。Spring AI、LangChain4j、Semantic Kernel 和 MCP Java SDK 都指向同一个趋势：模型只是链路中的一个节点，真正的工程难点在上下文、工具、权限、观测和失败处理。

RAG 和 Agent 不应只看 prompt 效果。对 Java 后端团队来说，更重要的是把向量库、检索策略、工具调用、业务接口权限和日志链路做成可维护的服务边界。今天的数据中，headroom 和 sdl-mcp 这类项目也说明，上下文压缩、代码库索引和 MCP 工具化正在成为独立工程方向。

招聘方向里反复出现 AI 平台、大模型工程、智能体应用和平台工程，说明 Java 开发者可以把既有后端能力迁移到 AI 工程场景：接口治理、限流熔断、权限控制、可观测性、任务编排、数据一致性仍然是核心竞争力。

近期可优先补三类能力：一是 Spring AI 或 LangChain4j 的基础集成；二是 MCP 和工具调用的权限设计；三是 RAG 质量评估与日志观测。相比追逐单个模型发布，这些能力更贴近日常业务落地。
